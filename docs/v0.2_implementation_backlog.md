## Epic 1: Tier 3 State & Memory Plane Integration (Supabase / Postgres)

### ISSUE-01: Tier 3 Database Schema, Migrations & RLS Functions
- **Component:** `src/adapters/supabase/migrations/`
- **Type:** Feature / Database Architecture
- **Estimated Effort:** 5 pts
- **Dependencies:** None
- **Acceptance Criteria Covered:** AC 2, AC 8, AC 9

#### Description
Author PostgreSQL DDL migrations for the durable Tier 3 entities defined in `docs/outside_orchestrator_role_v2.md` §5 and `Tier3_State_Memory`:
1. `factory_runs`: Stores tenant-scoped run envelope, lifecycle state (`created`, `provisioning`, `delegated`, `in_progress`, `evaluating`, `terminal`, `clean_terminated`, `quarantined`), parent Git SHA, budget, policy version, and state version.
2. `phase_envelopes`: Append-only records of inputs/outputs per phase attempt.
3. `leases`: Run/phase ownership, lease expiration timestamp, and monotonic `fencing_token` (`BIGINT NOT NULL DEFAULT 1`).
4. `memory_records`: Context records with tenant scope, SHA256 hashes, and embeddings metadata.
5. `events`: Transactional outbox table (`event_id`, `run_id`, `event_type`, `payload`, `sequence`, `published_at`).
6. `evidence_ledger`: Append-only storage for signed boundary evidence records.
7. `tournament_arms`: Isolated arm state preventing cross-arm overwrites.

#### Technical Details
- Implement helper functions:
  ```sql
  CREATE OR REPLACE FUNCTION public.get_claim(claim TEXT) RETURNS TEXT AS $$
    SELECT coalesce(
      current_setting('request.jwt.claims', true)::json ->> claim,
      current_setting('request.jwt.claim_' || claim, true)
    );
  $$ LANGUAGE sql STABLE;

  CREATE OR REPLACE FUNCTION public.current_run_id() RETURNS UUID AS $$
    SELECT (public.get_claim('run_id'))::UUID;
  $$ LANGUAGE sql STABLE;

  CREATE OR REPLACE FUNCTION public.current_tenant_id() RETURNS TEXT AS $$
    SELECT public.get_claim('tenant_id');
  $$ LANGUAGE sql STABLE;
  ```
- Enable Row-Level Security (RLS) on all tables. Enforce that authenticated runtime clients can query/mutate rows only where `tenant_id = current_tenant_id()` and `run_id = current_run_id()`.

#### Acceptance Criteria
- [ ] DDL applies cleanly on clean PostgreSQL 15+ / Supabase instance.
- [ ] Queries without valid claims return zero rows or throw permission errors under RLS.
- [ ] Attempting to insert a lower or duplicate fencing token into `leases` fails.
- [ ] `tournament_arms` rows are isolated by `(run_id, arm_id)`.

### ISSUE-03: External-Only Lease Manager & Silent-Sandbox Watchdog
- **Component:** `src/core/leaseManager.ts`
- **Type:** Feature / Distributed Systems
- **Estimated Effort:** 5 pts
- **Dependencies:** ISSUE-01, ISSUE-02
- **Acceptance Criteria Covered:** AC 2, AC 19

#### Description
Implement the external lease lifecycle and silent-sandbox watchdog. In v1, the Inside Orchestrator is completely lease-passive: it never renews leases, never touches fencing tokens, and cannot contest lease revocation. The Outside Orchestrator owns the entire lease lifecycle in Tier 3.

#### Technical Details
- In `src/core/leaseManager.ts`:
  - `acquireLease(runId: string, ttlMs: number): Promise<{ fencingToken: number; expiresAt: Date }>`:
    - Atomically increments `fencing_token` in `leases` table and sets new expiration.
  - `renewLease(runId: string, currentFencingToken: number, extensionMs: number): Promise<void>`:
    - Verifies token matches and extends lease timestamp.
  - `releaseLease(runId: string, currentFencingToken: number): Promise<void>`.
  - `startLivenessWatchdog(runId: string, options: { heartbeatWindowMs: number; onSilentSandbox: () => Promise<void> })`:
    - Monitors external observation signals (Warden probes, advisory polling).
    - If no activity is observed within `heartbeatWindowMs`, marks lease lost and triggers external stop path (SIGTERM sentinel -> teardown) without waiting for sandbox self-report.

#### Acceptance Criteria
- [ ] Acquisition fails if existing lease is unexpired and held by another active worker.
- [ ] Monotonic fencing token strictly increases on every acquisition.
- [ ] Silent sandbox exceeding liveness window triggers immediate teardown flow.
- [ ] Sandbox self-reports or forged callbacks cannot extend or alter the lease.

### ISSUE-04: Run State Machine & CAS Transition Guard (Transactional Outbox)
- **Component:** `src/core/stateMachine.ts`, `src/adapters/supabase/runsRepo.ts`
- **Type:** Feature / Core Orchestration
- **Estimated Effort:** 5 pts
- **Dependencies:** ISSUE-01, ISSUE-03
- **Acceptance Criteria Covered:** AC 1, AC 2, AC 7

#### Description
Implement the durable state transition engine with Compare-And-Swap (CAS) guards and transactional outbox. Every business-significant state change must be durably committed to Tier 3 before any outside action is initiated.

#### Technical Details
- Define transition guards in `src/core/stateMachine.ts`:
  ```typescript
  interface TransitionRequest {
    run_id: string;
    expected_phase: Phase;
    expected_state_version: number;
    target_phase: Phase;
    fencing_token: number;
    outbox_event: OutboxEvent;
  }
  ```
- Compare-And-Swap query pattern:
  - Updates `factory_runs` where `id = run_id AND phase = expected_phase AND state_version = expected_state_version`.
  - Increments `state_version`.
  - Inserts `outbox_event` into `events` table in the exact same SQL transaction.
  - Aborts with `ConflictError` if version or fencing token is stale.
- Recovery logic:
  - On orchestrator crash/restart, queries `factory_runs` + `leases` to determine active state and resume or abort stale runs.

#### Acceptance Criteria
- [ ] Out-of-order or duplicate phase advance requests are rejected with explicit conflict.
- [ ] State transition and event outbox write are strictly atomic.
- [ ] Stale worker with lower fencing token is denied mutation.
- [ ] Restart recovery correctly reconstructs execution state from Tier 3.

### ISSUE-07: Pull-Based Advisory Output Collector & Manifest Verifier (v1 Pull Model)

- **Type:** Feature / Ingestion
- **Estimated Effort:** 5 pts
- **Dependencies:** ISSUE-06
- **Acceptance Criteria Covered:** AC 18

#### Description
Implement the pull-based advisory output collector. In v1, the Inside Orchestrator never pushes trace or result packages to the Warden. The Warden must pull advisory data (trace JSONL, status events, and result archive) over the private `tag:edge-control-prod -> tag:factory-sandbox:8787` broker path or host-side filesystem before VM destruction, verify manifest hashes, and record evidence.

#### Technical Details
- In `src/warden/advisoryCollector.ts`:
  - `collectAdvisoryOutput(target: { tailscaleIp: string; port: number; outputDir?: string }): Promise<AdvisoryPackage>`:
    - Pulls `trace.jsonl` and `result_package.tar.gz` (or directory manifest).
    - Computes `actual_result_sha256 = SHA256(result_package)`.

#### Acceptance Criteria
- [ ] Successfully pulls and validates result archives matching trace manifests.

### ISSUE-08: Host-Side Effect Reconciliation Gate (ERG) & Git Tree Verifier
- **Component:** `src/core/erg.ts`, `src/utils/git.ts`
- **Type:** Feature / Safety & Verification
- **Estimated Effort:** 5 pts
- **Dependencies:** ISSUE-06
- **Acceptance Criteria Covered:** AC 5

#### Description
Implement the Effect Reconciliation Gate (ERG). The sandbox's `declared_changed_files` list is an unverified claim. The Warden independently observes the host-side git worktree transition, computes actual before/after tree hashes, and enforces zero tolerance for undeclared touches.

#### Technical Details
- In `src/core/erg.ts`:
  - `reconcileTreeEffects(params: { repoPath: string; baseSha: string; declaredChangedFiles: string[]; allowedPaths: string[]; immutablePaths: string[] }): Promise<ErgResult>`:
    - Computes post-execution tree SHA using `git write-tree`.
    - Runs `git diff-tree -r --name-only baseSha postTreeSha` to identify actual changed files.
    - Asserts that every actual changed file exists in `declaredChangedFiles`.
    - Asserts that every changed file matches `allowedPaths` glob patterns.
    - Asserts that no file in `immutablePaths` (e.g. `AGENTS.md`, `.github/`, test suites) was touched.
    - Emits signed `erg_result` event into evidence ledger.
    - If undeclared modifications exist: returns `{ passed: false, unauthorizedTouches: [...] }` and blocks harvest.

#### Acceptance Criteria
- [ ] Passing case: exact match between declared and observed files within allowed paths.
- [ ] Rejects runs where sandbox touched an undeclared file.
- [ ] Rejects runs where sandbox touched any file matching `immutable_paths`.
- [ ] Records before/after tree SHAs and diff in signed boundary evidence.

## Epic 5: Teardown, 12-Predicate Attestation & Harvest Control

### ISSUE-14: 13-Step Teardown Orchestrator & Stale Callback Rejector
- **Component:** `src/core/teardownManager.ts`
- **Type:** Feature / Teardown & Lifecycle
- **Estimated Effort:** 5 pts
- **Dependencies:** ISSUE-03, ISSUE-06, ISSUE-09, ISSUE-10
- **Acceptance Criteria Covered:** AC 7, AC 11, AC 17

#### Description
Implement the authoritative 13-step teardown orchestrator (`Warden_Policy` §6). Teardown is an active security operation, not passive garbage collection. Must execute across all terminal paths (completion, cancellation, timeout, policy violation).

#### Technical Details
- In `src/core/teardownManager.ts`:
  - Execute sequential teardown steps:
    1. Mark run terminal / `teardown_pending` in Tier 3.
    2. Revoke delegation and runtime credentials via broker.
    3. Signal Inside Orchestrator to halt child processes (SIGTERM/sentinel).
    4. Pull and collect remaining advisory trace package.
    5. Deauthorize Tailscale node via API.
    6. Confirm Tailscale node absence from tailnet active inventory.
    7. Destroy exe.dev VM via API (`rm`).
    8. Confirm exe.dev VM absence via provider API (`ls`).
    9. Run post-teardown active network probes.
    10. Verify no post-teardown callbacks or writes accepted.
    11. Evaluate 12-predicate `CLEAN_TERMINATED` attestation.
- Any subsequent callback received after teardown initiation is rejected with `TerminalStateError` and logged as a stale-callback boundary event.

#### Acceptance Criteria
- [ ] Teardown initiates reliably on timeout, user cancel, policy violation, and success.
- [ ] Incomplete step transitions state to `TEARDOWN_FAILED` or `QUARANTINED`.
- [ ] Post-teardown callbacks are rejected and logged.
- [ ] All 13 steps record corresponding signed boundary evidence.
